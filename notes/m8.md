- Benchmarks were last measured as a set at M4's close, on Linux only:
  b1-b13 all beat bash 5.3, the weakest being b13 printf (2.3x), b11
  globbing (3.7x) and b1 arithmetic (4.1x). Windows numbers (agent
  batch, startup, against Git Bash and busybox sh) date from M5a.
  There is no bash-completion sourcing benchmark and no configure-style
  macro benchmark yet.
- Editor: emacs mode with history, completion and inputrc basics (M6).
  `editing-mode vi` is recorded but has no effect; vi-* functions bind
  nothing. No `bind`, `complete` or `compopt`; `compgen` lists names
  (-a -b -c -d -e -f -g -j -k -s -u -v and -A) only.
- inputrc: variables and key bindings, no `$if`/`$include`, no macros.
- The oracle manifest (t/oracle-posix.txt) has four FAILs: builtins
  (our help text, accepted), complete (this milestone), dollars
  (accepted), history (bash -i on a non-terminal, this milestone).


## Principles

1. bash 5.3 is the reference: recorded specs (t/exec, t/edit through
   tools/edrecord against bash's readline), the oracle suite, and Git
   Bash for msys behaviour. Readline's and bash-completion's sources
   and documentation are read for semantics only, never copied (GPL).
2. Performance work starts from measurements, not guesses: bench/run
   with outputs compared by checksum before anything is timed, and a
   profile before any optimization. A change that makes a benchmark
   slower than at the start of M8 needs a reason in this file.
3. bash-completion is a test input like bash's own suite: fetched into
   a scratch directory, never committed.
4. Testing rules stay: randomized tests only on the vos; real
   processes, terminals and signals only in the oracle container, the
   sandbox, or curated scripts on Windows and XP.


## Steps

Waves: 1; then 2 to 4 (performance) and 5 to 8 (editor) in any order,
9 after 8; 10 at any time; then 11.

1. **Baseline.** bench/run on Linux against bash 5.3 and on Windows
   against Git Bash and busybox sh, plus startup and the agent batch.
   Add the missing macro benchmarks: sourcing bash-completion (B14) and
   a configure-style workload. Record the table here and choose what
   needs work.
2. **I/O.** Read-ahead for foreign pipes on Windows (and the shared
   reader issues in issues.md), output coalesced to regular files
   (flushed before any spawn, block or exit), and whatever the baseline
   shows.
3. **Memory.** `os_decommit` for arenas past a high-water mark, the
   regex RxEntry bound, copy-on-first-write for fiber copies, 32-bit
   tuning on the i686 build.
4. **Launcher fibers.** An external pipeline stage whose words hold
   `$(...)`, a procsub, a funsub or `@P` gets a launcher fiber instead
   of a full vproc (m3a.md), fixing the comsub-waits-on-a-later-stage
   hang.
5. **bind.** The builtin in full (`-l -p -P -v -V -s -S -q -u -r -f -x
   -X -m`, `keyseq:function`, macros, `-x` shell commands with
   READLINE_LINE/READLINE_POINT/READLINE_MARK), and a binding cache.
6. **inputrc.** `$if`/`$else`/`$endif`/`$include`, macros, null prefix
   bindings, and effect for the variables now only recorded where
   bash's behaviour shows it.
7. **vi mode.** vi-insert and vi-command keymaps, motions, operators
   with counts, undo, `.`, searches, `v` (edit-and-execute), mode
   strings with show-mode-in-prompt.
8. **Programmable completion.** `complete`, `compgen` and `compopt` in
   full: -F and -C with the COMP_* variables and COMPREPLY, -D -E -I,
   the -o options, filtering and prefixes; dabbrev-expand and
   export-completions; the suite's complete test.
9. **bash-completion.** Source a current bash-completion release and
   complete common commands through it (edit specs, recorded from
   bash); B14 must beat bash.
10. **Job control and terminal leftovers.** Shell-code pipeline stages
    that stop under `set -m` (a foreground job in an image child that
    leads the group), Win32 fg's Ctrl-C through a job object per
    background program, and `bash -i` reading a non-terminal with
    readline's own redisplay bytes (the history test).
11. **Closing.** The benchmark table with every benchmark beating bash
    5.3, Git Bash and busybox sh; suites green; Windows and XP checks;
    issues.md has no M8 items.

So every benchmark already beats all three shells. The work is in
the regressions since M4 (b6 and b12, about 30% and 45% on the same
machine, confirmed against a build of 541c565: a here-document into
`read` is 3.5x slower), the narrowest margins (p5 1.6x over busybox,
b13 2.2x and b11 3.5x over bash), and the benchmarks not written yet
(startup and the agent batch again, B14 bash-completion, a
configure-style workload).

The regressions since M4, found by timing every tenth commit from
541c565 and then each commit of the last stretch:

- read's field scans (c7e7c12's per-character IFS) compared every byte
  through the multibyte matcher, even with IFS empty. An ASCII IFS
  matches no part of a multibyte character, so the scans use a byte
  table again unless IFS holds a multibyte character.
- read asked isatty on every call (an ioctl per line from a pipe); a
  File now caches the answer.
- varchanged, run on every assignment (an arithmetic for loop's `i++`
  too), compared the name with about 28 special names, growing through
  M6 and M7. A switch on the first byte now turns most names away.

Afterwards b6 2.50 s against M4's 2.48 s and b12 1.13 s against 1.12 s;
an empty `for ((...)); do :; done` of a million iterations is still 5%
slower than M4 (0.394 s against 0.375 s), from no single commit.
