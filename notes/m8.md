## Principles

1. bash 5.3 is the reference: recorded specs (t/exec, t/edit through
   tools/edrecord against bash's readline), the oracle suite, and Git
   Bash for msys behaviour. Readline's and bash-completion's sources
   and documentation are read for semantics only, never copied (GPL).
2. Performance work starts from measurements, not guesses: bench/run
   with outputs compared by checksum before anything is timed, and a
   profile before any optimization. A change that makes a benchmark
   slower than at the start of M8 needs a reason in this file.
3. bash-completion is a test input like bash's own suite: fetched into
   a scratch directory, never committed.
4. Testing rules stay: randomized tests only on the vos; real
   processes, terminals and signals only in the oracle container, the
   sandbox, or curated scripts on Windows and XP.

### Step 2: I/O

Measured first (Windows 11, 200,000 lines, ms):

| loop | before | after |
|---|---|---|
| `echo` into a file opened once | 688 | 252 |
| read from a regular file | 812 | 750 |
| read from a pipe (`cat f \| while read`) | 1051 | 324 |
| read from a procsub (`done < <(cat f)`) | 960 | 241 |
| bare loop, for scale | 93 | 93 |

Linux: `echo` into a file 273 ms before, 195 after (bash 5.3: 758).

Floors, measured with small C programs: a WriteFile of 55 bytes 1.5 us,
GetConsoleMode on a file 0.5 us, GetFileType 0.1 us, ReadFile of 128
bytes plus the seek back 1.3 us, and CreateFile, WriteFile and
CloseHandle 67 us (antivirus). So `echo x >>f` in a loop, 73 us a line
here against 2.7 on Linux, is the system's cost: nothing to win.

- **Coalesced output to regular files** (main_win32.cpp, main_posix.cpp):
  one pending buffer (16 KiB) for one disk file. os_write to it
  appends; any other platform call flushes first (spawn, fork, wait
  that may block, open, stat, list, read, seek, close, dup, exec,
  writes to anything else), as do full buffers, the first write 100 ms
  after the buffer began, the exits and os_oom. Signal polls, rlimit
  and isatty do not flush: the core asks them every command, and they
  observe no file. A failed flush fails the handle's next write. The
  vos stays unbuffered; the POSIX build runs every t/exec spec under
  RECORD_CHECK, t/exec/936 checks ordering through other descriptors,
  stats, programs, pipes, subshells and jobs, and t/win32/020 the same
  on Windows plus the 100 ms rule.
- os_write asked GetConsoleMode of every handle not registered as a
  console; it asks GetFileType first now, and only a character device
  can be a console.
- read caches whether its File seeks (File.seek), as it does for tty.
- **Read-ahead on Windows pipes** (main_win32.cpp): a pipe's read end
  that this shell made (os_pipe) is read a block (16 KiB) ahead once
  the shell has read it 16 times without lending it to a child. Bytes
  read ahead still go first to the next reader: a child that takes the
  pipe gets an interposed one (the M3b machinery), and the streak
  starts over, so a loop starting a program on the pipe each time keeps
  reading exactly. Inherited pipes may have other readers and are never
  read ahead. Both the direct and the scheduler's read paths count and
  fill. t/win32/021, its output equal to bash 5.3's on Linux.
  Before, a line cost three calls (os_peek's PeekNamedPipe, os_read's
  PeekNamedPipe and ReadFile).
- POSIX: os_peek asked fstat on every call (two a line from a pipe);
  the per-descriptor kind cache now records FIFOs too (5-10% on pipe
  read loops). `-DPROFILE -pg` builds write gmon.out (exitwith calls
  exit).
- **Constant words** (expand.cpp, literalword): profiling p5 found
  expandwords at 37% of the run, as every word took the whole path
  (brace check, a fresh X, a flag byte per character, splitting, a
  glob check) even `kind`, `[` or `-lt`. A word none of whose bytes
  starts an expansion, a quote, a tilde, a brace expansion, a pattern
  or procsub, or is a CR is its own field now, with no copy (literal
  text never splits, whatever IFS holds). expandstring, expandpattern
  and expandpat return such text as it is too: it means itself in every
  context (assignment values, the case word, patterns, arithmetic).
  p5 0.305 s to 0.240, b13 0.304 to 0.221 on Linux; b1 and b2 unchanged.
- **Simple parameter words** (expand.cpp, simpleexpand): `$name`,
  `${name}`, `"$name"` and `"${name}"` with a plain identifier skip the
  machinery when the answer is plainly at most one field: quoted, or
  unquoted with no byte of IFS and none of `* ? [ ( \`, CR or NUL (an
  unquoted empty value is no field). Namerefs, specials, positionals
  and an unset name under set -u take the full path. The value is
  copied, since a for loop's word list outlives a reassignment.
  t/exec/937. On Linux, best of 7 against the previous commit: p5
  0.337 s to 0.285, b13 0.268 to 0.225; b1 and b2 unchanged.

### Step 3: memory

- **Decommit** (os_decommit; unabashed.cpp, arenatrim): after each
  command the outermost reader (runsource without an outer lexer)
  gives back the scratch arena's pages more than 8 MiB past its front
  once over 32 MiB is committed past it. Copies of an arena made
  before may believe in the old commit, so nothing under the commit at
  the loop's start goes, and nothing a command's own copies still use
  (they are gone when the loop resets). Win32 MEM_DECOMMIT; POSIX maps
  PROT_NONE over the range; the vos poisons it. Linux, a 50 MB
  `$(...)` then another: RSS 263 MB after the first and 125 MB (the
  value in the store) after trimming, against 263 MB before. The
  store, with its size-class free lists, keeps its pages.
- **Regex span records bounded** (regex.cpp, rxrecord): the
  back-references' spans and their trie share the memo's bound, half
  of memomax. Past it the search gives up as glibc does when malloc
  fails (REG_ESPACE): rxexec returns -2 and `[[ =~ ]]` takes it for no
  match, as bash takes any regexec error. No recorded case comes near
  it; `(a*)(a*)\1\2x` on 600 a's still matches, in 8.7 s (10.6 s at
  M4). regex_test checks the bound with an 8 MiB arena.
- **Copy-on-first-write for fiber copies: not done.** Measured first:
  a shell-stage pipeline copies the store, 0.33 ms with 5,000
  functions and 5,000 variables, 12 us with bash-completion loaded
  (170 functions, whose bodies are shared code blocks), against 390 us
  for bash's fork there. Sharing would need every write to a shared
  store, the parent's journalled ones included, to copy for each
  sharer first; not worth the risk for this.
- **32-bit address space.** Each depth's scratch pool reserved the full
  256 MiB, so eight nested `$(...)` ran out of address space on the
  i686 build. Now depth 1 (most comsubs) reserves half and deeper ones
  what a vproc gets (the scheduler's sixteenth). The i686 build is
  large-address-aware (4 GiB under x64 Windows). A build taking every
  reservation top-down (MEM_TOP_DOWN, so pointers above 2 GiB) passed
  t/win32 except 012, which fails with the plain i686 build on Windows
  11 too (issues.md).
- XP: 010-writes failed. It flakes at earlier commits as well; the
  cause is not found (issues.md has what was measured).

### Step 4: launcher fibers

- The hang: an external stage before the last starts directly when
  its words seem to run no shell code, expanding them before the
  stages to its right start. runscode saw `$(`, backquotes, procsubs,
  funsubs and `@P`, but not code hidden in a value: arithmetic
  (`$((...))`, `$[...]`, subscripts, substring offsets and lengths)
  evaluates variables' values as expressions, and a subscript there
  may hold a comsub (`i='a[$(cmd)]'; prog ${a[i]}`), as may the target
  of `${!x}` or of a nameref. Such a comsub waiting on a later stage
  (through a FIFO) waited forever. proc.cpp's hiddencode now sends any
  stage with `$((`, `$[`, `${!`, a subscript other than digits, `@` or
  `*`, an arithmetic `:` in a braced expansion, or a nameref to a vproc
  stage, which runs concurrently. t/exec/938, recorded from bash; the
  vos's FIFOs do not block, so only RECORD_CHECK on the Linux build
  catches the hang (issues.md).
- **Launcher fibers: not done.** They were to make such stages
  cheaper than a full vproc, whose cost is copying the store: 12 us
  per stage with bash-completion loaded (step 3), against bash's fork.
  A stage with command_not_found_handle defined stays a vproc for the
  same reason.

### Step 5: bind

- inputrc.cpp's b_bind: every option of bash 5.3's (`-l -p -P -s -S
  -v -V -X -q -u -r -f -x -m`, then `keyseq:function` and inputrc
  lines as arguments), with bash's messages, statuses and listing

  each call warns first, `-p` and `-P` list in byte order of the

- The editor names all 176 of readline's functions (bash's included),
  so bind and inputrc bind them all; the ones not implemented ring
  the bell (issues.md, for steps 6 and 7).
- Default keymaps checked against `bind -p` from bash with no
  terminal and no inputrc, in all five keymaps: added the keyboard
  macro keys, C-x C-v, M-x, C-x s and M-&; vi-insert and vi-command

  Insert, Home and End as `\e[N~`, and Page Up/Down, which bash gets

- `bind -x`: the command runs with READLINE_LINE, READLINE_POINT,

- The plan's "binding cache" is the variable-lookup cache (design
  critique C1), not key bindings: evaluated in step 11 with the other

### Step 7: vi mode

- `set -o vi`, `bind 'set editing-mode vi'` and the vi-editing-mode
  and emacs-editing-mode functions switch the editor and keep the set
  -o options in step. Each line starts in insert mode; ESC (vi-movement-
  mode) enters command mode with the cursor kept on the last character.
- Every vi-* function of readline and bash, with counts: the word,
  WORD and end motions, f F t T ; , (vicsearch), %, |, marks (m, `),
  the operators c d y with any motion and their doubled forms (cc dd
  yy, and c and d with a count before or after), x X s S C D r R ~,
  p P with counts and M-y (vi-yank-pop), undo (u, U as revert), `.`
  redoing the last text change with its count and insert text, the
  non-incremental `/` `?` `n` `N` searches (glob patterns, as bash's
  vi search), `#`, `@` running the alias `_c` as keys (bash's
  posix-edit-macros), `_` (vi-yank-arg), `v` (edit-and-execute with
  $VISUAL or $EDITOR, `fc -e vi` in POSIX mode, a count naming the
  history entry), `*` `=` `\` (vi completion), C-w and the terminal's
  werase in insert mode (vi-unix-word-rubout), and C-v.
- Replace mode (R) builds its keymap once, a copy of vi-insert with
  printing keys overstriking and the kill and yank keys their
  overstrike forms; bracketed paste overstrikes too.
- show-mode-in-prompt draws emacs-mode-string, vi-ins-mode-string or
  vi-cmd-mode-string (replace mode counts as command) before the
  line's own prompt, not a search's.
- ESC in command mode waits keyseq-timeout for a sequence (bind -m
  vi-command '"\ey": ...' makes it a prefix) and then does nothing, as
  readline's null shadow; vi completion rings no bell on an ambiguous
  word, as readline doesn't in vi mode.
- Named alone, vi-bword, vi-fword and vi-eword run their capital forms:
  readline looks names up ignoring case and finds those first.
- Found by 076 on Linux: under job control, a pipeline whose only
  program is its last stage (`set -o | grep x`) left that program's
  group holding the terminal, and the next read failed as end of
  input; the shell now takes the terminal back after every grouped
  pipeline.

### Step 8: programmable completion

- pcomplete.cpp holds the compspec table (bash's hashlib order, so
  `complete -p` lists as bash does; copied on first write in a
  concurrent vproc), `complete`, `compgen` and `compopt` with every
  option and bash's messages, the action generators (aliases to
  variables, signals, jobs, services, users and groups, bindings),
  -G -W -P -S -X (with & and !), -F and -C, and the -o options.
- A -F function gets $1 $2 $3, COMP_LINE, COMP_POINT (in characters),
  COMP_TYPE, COMP_KEY, COMP_WORDS split at COMP_WORDBREAKS as bash
  splits them, and COMP_CWORD; status 124 retries the lookup (up to 32
  times, then bash's warning); a missing function gives bash's message
  and the line drawn again. -C runs through a capture, its lines
  joined at backslash-newlines.
- At the prompt the compspec is chosen as bash does: -E on an empty
  line, -I for the command word (and after a separator), none after
  assignments alone, then the name, its basename and -D. bashdefault
  and default fall back to bash's own completion and to file names;
  filenames, noquote, nospace, nosort, fullquote, dirnames and
  plusdirs set how the matches are handled. progcomp_alias replaces
  an alias with its value and tries again (an alias whose value starts
  with its own name loops to the warning, as bash's does).
- dabbrev-expand is menu completion over the words of history, newest
  line first, unsorted (adjacent duplicates dropped) and with nothing
  appended; it continues a menu-complete, as readline's does.
  export-completions writes the count, the word, its span and the
  matches below the line and leaves the display as it was, as
  readline does; with an argument above one it also clears the line.
  The editor now moves left by a carriage return and a forward move
  where readline reckons that shorter, so the screen after such output
  matches.
- A completion claims a scratch depth, so that command substitutions
  in a -F function take the next one (sharing it looped forever, found
  by bash-completion); $? and PIPESTATUS are kept across it, and a
  compspec comes before $ variable completion, as bash's order.
- t/exec/940 to 942 (complete, compgen, -F and -C), t/edit/077 to 080,
  recorded.

### Step 10: job control and terminal leftovers

- An interactive shell whose input is no terminal reads it with the
  editor, as bash's readline does: the keys edit (C-p, C-r, C-o), what
  is typed is echoed after the prompt on standard error, drawn as on a
  dumb terminal COLUMNS wide (80 without it), and the end of input
  prints "exit" after the prompt. Where readline draws only what
  changed, the editor writes just what was added at the end, so plain
  typing gives readline's bytes; other changes redraw the row. The
  input is read a byte at a time, so commands that read it get the
  rest. Input from a terminal with standard error elsewhere still reads
  plainly. "cannot set terminal process group" is now printed under -n
  too, as bash does (history7's `-in`). t/exec/943, recorded; the
  oracle's history test now fails only as bash does.
