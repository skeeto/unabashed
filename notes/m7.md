   t/posix), its own test suite in the oracle container, and Git Bash

   the same container: the environment's doing) or FAIL. A test never
   moves down; the exit criterion freezes the list with categories d

   builtins/*.def or its documentation (GPL).

   processes, terminals and signals only in the oracle container, the
   sandbox, or curated scripts on Windows and XP.

## Decisions

### Job control on POSIX (step 7 design)

Today (64ea0d1): there are no process groups, no tcsetpgrp, and no
WUNTRACED. SIGCHLD has SA_NOCLDSTOP. `set -m` is only a flag (it
turns off lastpipe and keeps a job's stdin). fg, bg and suspend say
"no job control". Notifications follow bash's non-interactive rules
only. The vos has no process groups and no stopped state.

**Platform API**
- `Spawn.pgid`: 0 keeps the shell's group, -1 makes a new group led by
  the child, and >0 joins that group. `Spawn.foreground`: the child
  takes the terminal. As bash does, both parent and child call
  setpgid, and both call tcsetpgrp for a foreground job, so there is
  no race either way. The image spawn of `&` (forkimage) honours the
  same fields.
- `os_tcpgrp(os, fd, pgid)`: with pgid 0, return the terminal's
  foreground group; with pgid >0, set it, with SIGTTOU blocked around
  the call. `os_setpgid(os, pid, pgid)` exists for the shell itself.
- Stops are reported. SIGCHLD loses SA_NOCLDSTOP, and the IO_PROC
  waitpid and os_waitproc pass WUNTRACED. A stop yields
  `WSTOPPED|sig`, which is not a final status: the waiter can wait
  again. Resuming a job is `os_kill(-pgid, SIGCONT)`, so a negative
  pid means the group, as in kill(2). `kill %1` sends to the job's
  group when it has one.
- `Tty` gains `susp`, for prompts and `stty`-like reporting.

**The shell under job control** (`set -m`, or interactive with a
terminal):
- At startup, or when `set -m` turns it on, the terminal is fd 2 if
  it is a tty, else /dev/tty, as bash's shell_tty. The shell puts
  itself in its own group, takes the terminal, and ignores TSTP, TTIN
  and TTOU (an interactive shell only; a script under `set -m` keeps
  their defaults, as bash). The original group and foreground are
  restored at exit. With no terminal, `set -m` still makes groups but
  gives no terminal away (bash's behaviour in its jobs test).
- Each job is a process group led by its first process. Job gains
  pgid, a state (RUNNING, STOPPED, DONE) and the pids of its
  processes. A foreground job holds the terminal while the shell
  waits, and the shell takes it back after, also restoring the
  terminal modes saved before the job ran (bash's
  get/set_tty_state).
- A foreground pipeline creates a Job record only when it stops (bash
  numbers it then). A stop ends the wait: the job becomes STOPPED and
  current, "\n[N]+  Stopped                 text" is printed, and the
  status is 128+sig. The jobs list shows it as Stopped(SIGTTIN) etc.
  for stops other than TSTP.
- `fg` gives the terminal, sends SIGCONT to the group, prints the
  command text, and waits as for a foreground job. `bg` sends SIGCONT
  and prints "[N]+ text &". `%N` as a command is `fg %N`, and
  `%N &` is `bg %N`. `wait` on a stopped job returns 128+sig
  immediately (bash's behaviour with job control), and `wait -f`
  waits for termination. `suspend` stops the shell itself with
  SIGSTOP, and refuses in a login shell without -f. On exit, an
  interactive shell with stopped jobs says "There are stopped jobs."
  once; the next exit sends SIGHUP and SIGCONT to them.
- **Shell parts of a foreground job.** A stage on the main stack or on
  a fiber cannot be stopped. Bash forks every subshell, so under job
  control (and only then) a foreground pipeline of two or more stages,
  a foreground `( ... )`, and a foreground `$(...)`-free simple command
  that is a function or builtin within a pipeline all run in one
  forked child shell. That child is the job's group leader, and it
  runs the pipeline as today, on fibers, with its externals in its
  group. This reuses the image path (forkimage on POSIX), waited in
  the foreground instead of as `&`. It is semantically safe because
  monitor mode already disables lastpipe, so every stage is a
  subshell anyway. A lone external keeps the direct spawn with
  `pgid -1`. A lone builtin, function or compound command runs in the
  shell as today: Ctrl-Z stops only the external it is waiting for,
  and the loop goes on, as in bash.
- Notification: an interactive shell prints changes in job state
  ("[1]+  Done   text") before the prompt, and `set -b` prints them at
  once. A script under `set -m` prints them when jobs are next polled,
  as bash's notify_and_cleanup does. The exact rules are checked
  against bash with probes while implementing.
- Builtin messages: without job control, fg and bg say "no job
  control", or "job N started without job control" for a job that
  exists. Other messages: "no current jobs", "%2: no such job",
  "job 1 already in background", and `-s: invalid option` with the
  usage line.

**vos model** (needed by the specs): VProc gains a pgid and a
VP_STOPPED state that vpick skips. TSTP, TTIN, TTOU and STOP stop a
fake whose disposition is the default, and CONT resumes it. A wait
with WUNTRACED reports the stop. kill(-pgid) signals the group. The
VTty has a foreground pgrp: ^Z sends TSTP and ^C sends INT to that
group only. A background process that reads the tty gets TTIN.
Shell VProcs (image spawns) stop the same way.

**Order**
- 7a: fg, bg, jobs and the %N commands for running jobs, with their
  messages (shared with Windows, step 8).
- 7b: the platform API and vos model, with unit tests.
- 7c: groups, the terminal, stopped jobs, fg/bg/suspend/wait, and the
  exit warning.
- 7d: forked foreground pipelines and subshells under monitor mode.
- 7e: notifications; the jobs and errors oracle tests; specs (vos
  scripted ^Z); a manual check of a real terminal on Linux through
  WSL.

### Step 2: remaining builtins

- ulimit: `os_getrlimit`/`os_setrlimit` in the platform API, in
  bash's `-a` order (RL_*), values in the system's units. POSIX uses
  getrlimit/setrlimit (the pipe size is PIPE_BUF and cannot be set);
  the vos models the oracle container (nofile 1024, stack 8 MiB, ...)
  or, in its Windows personality, the Win32 layer's table; Win32 keeps
  a table modelled on Cygwin's (Git Bash's `ulimit -a`), where only -c
  -s -v -n take a value and the stack is the PE's own reservation.
  Limits with no counterpart (err E_NOSYS) make their option letter
  invalid, as -e is in Git Bash.
- The shell keeps a table (Shell.rl). At the top level ulimit sets the
  process; a subshell, which is no process of its own here, changes
  only its table under the kernel's rules and hands it to the programs
  it starts (Spawn.rlimits): bash's forked subshell, observed.
- bash's parsing: each resource letter takes the rest of its word or
  the next word not starting with '-'; a leftover operand goes to the
  last resource without one; more than one resource prints rows with
  descriptions; the first error ends the command.
- Found on the way: the POSIX spawn moved descriptors through
  F_DUPFD 256, which fails once `ulimit -n` is 256 or less; sources now
  move just above the highest target (fdbase).
- procsub passes the oracle now (it was waiting on ulimit).
- pushd, popd and dirs: the stack below the working directory is
  Shell.dirs, bottom first, replaced rather than changed in place so a
  subshell's changes roll back with its Shell copy. They run cd under
  their own names. bash's quirks kept: number and option arguments are
  whole words ("-lv" is an invalid number), `pushd -n +N` loses the
  entry that would have become the working directory, `pushd` with no
  arguments changes the stack even when cd fails. ~N and DIRSTACK
  (reads, and DIRSTACK[N]=dir for N > 0) use the same indexing. The
  dirstack oracle passes.
- enable: a disabled-builtin bitmask in the Shell (so per subshell);
  findbuiltin skips disabled ones, enable itself sees all. No loadable
  builtins: `-f` says "dynamic loading not available" (bash without
  dlopen), `-d` reports "not dynamically loaded" as bash with dlclose
  does for every static builtin. `source` is a special builtin, as in
  bash's lists. Listings match bash's except bind, complete, compopt
  (M8) and help (step 3), which we lack yet.
- The builtins test's messages: symbolic umask modes (bash's chmod-like
  grammar applied to the mask's complement; `umask -S mode` prints the
  result); hash -p refusing a directory and skipping names with a slash;
  source keeping positional parameters a sourced file set (outside a
  function) when it was given arguments; POSIX mode's `.`: no search of
  the working directory, a missing or unreadable file ends a
  non-interactive shell unless `command` ran it (Shell.viacommand); a
  file found through a -p or PATH entry goes by that path ("./f"). What
  remains of the builtins test is help.


### Step 3: help

- help.cpp: one table of the 77 topics bash has (builtins, keywords,
  `variables`), sorted as bash sorts them, each with bash's synopsis
  (an interface: usage messages print it, and usage() now falls back
  to it) and a description written for this project. The first line is
  the summary help -d and -m show.
- Layout copied from observation: the two-column listing at COLUMNS/2
  (80 when unset), the left column cut at width-3 and the right at
  width-4 with a `>` (shown even when nothing was cut at exactly that
  length, as bash's does), a `*` for a builtin enable turned off.
  Matching: exact or pattern first, else prefix; the "Shell commands
  matching keyword(s)" header for a pattern; bash's no-match message.
  The header and help -m's IMPLEMENTATION section are our own text.
- NAME --help runs through runbuiltin for every builtin except those
  bash leaves alone (:, echo, true, false, test, [) and cygpath:
  synopsis and description, status 2.
- The listing ignores a failed write (`help >&-` is silent with status
  0), as bash checks only the other forms (Shell.nowriteerr).
- vredir: `{v}` redirections fail when `ulimit -n` puts fd 10 out of
  reach, with bash's two messages; vredir now fails only as bash does
  in the container. The builtins test differs now only in help's
  descriptions, which by design are not bash's.

### Step 4: invocation

- Two passes, as bash: long options first (`--name` or `-name`, the
  16 bash lists), then the short ones. A long option after a short one
  is the letter `-` to the second pass: "--: invalid option". A bad
  long option or letter prints the usage (to stderr, status 2); the
  usage text is an interface and matches bash's, `--help` adds our
  version line and two pointers to `help`, `--version` our version
  line and a public domain notice. Both act before any short option.
- `--verbose` is `set -v`, `--debug` nothing, `-r`/`--restricted` are
  recorded for step 5 (`+r` is an error, as bash's). `-O` names wait
  until after the interactive setup, as bash applies them; a bad name
  now exits 2 even with `-c` (it was 127, the fatal-error rule).
- `-D`, `--dump-strings`, `--dump-po-strings`: the lexer reports each
  `$"..."` as a MSG_DUMP message (at the token, and in the nested
  `${...}` form), runsource prints it to stdout as written or as a po
  entry citing the input and line, and the shell runs nothing (`-n`).
- `--pretty-print`: a script or stdin is parsed and each command
  printed as bash's make_command_string does in POSIX mode, a blank
  line for a run of empty ones and at the end; a syntax error is status
  1. `-c` just runs; an interactive shell warns and runs.
- `--debugger` sources bashdb's start file with extdebug, or says why
  not and goes on.
- A script named without a slash that is not in the working directory
  is looked for along PATH (any regular file); messages use the found
  name, `$0` the given one.
- BASH_ARGV0 from the environment sets `$0` (the dynamic variable used
  to hide it).
- "bad interpreter": when the kernel refuses an executable file, a
  `#!` line's interpreter is named (CR as `^M`), status 126; without
  one, ENOENT is "cannot execute: required file not found", 127. The
  vos now fails a `#!` naming a missing file with ENOENT, as Linux
  does, so the path is testable; a `#!` naming a present file still
  runs as before.
- Functions: a name with a slash is called outside POSIX mode;
  `export -f` refuses names with `/` or `=` ("cannot export"), and
  such names, or (POSIX mode) non-identifiers, are not imported.
- invocation passes the oracle; exportfunc's one difference is the
  eval line count (issues.md). execscript's remaining difference is
  bash's process group number in a message, which varies run to run.

### Step 5: restricted shell

- Restricted when named rbash (argv[0]'s base, a leading `-` and
  `.exe` dropped), with `-r`/`--restricted`, or after `set -r`. The
  startup files run unrestricted; then PATH, SHELL, ENV, BASH_ENV and
  HISTFILE become readonly (created unset if need be) and
  Shell.restricted is set. Shell.rshell (shopt restricted_shell, which
  shopt cannot change) says it started so; it is known before the
  environment is imported (startsrestricted scans the arguments), as a
  restricted shell takes no functions, SHELLOPTS or BASHOPTS from it.
- Refused, with bash's messages: cd/pushd/popd; a command name with a
  slash (functions and builtins of such names still run); `.` with a
  slash or `-p`; every write redirection to a file, `/dev/null` too
  ("restricted: cannot redirect output", before set -C's check);
  `exec` with a command; `command -p` (even with -v); `hash -p` and
  `BASH_CMDS[x]=` with a slash, or naming what PATH cannot find;
  `enable -d` and enabling a disabled builtin; `history` file
  operations on a name with a slash (HISTFILE's default included);
  `set +r` (status 1, bash's change_flag failure). `$-` shows `r`.
  No functions are exported.
- A script run without `#!` (in-process subshell) is unrestricted, as
  bash turns the flag off in its child.
- rsh passes the oracle.

### Step 6: POSIX mode

- An unquoted `$@` or `${a[@]}` in an operator's word, with IFS set,
  non-null and not starting with a space, is the elements joined by
  spaces as if quoted (POSIX interp 888, putlist). `$*` still splits.
- `${!?}` and `${!#}` are `$!` followed by an operator in POSIX mode.
- An arithmetic expansion error in a POSIX non-interactive shell is
  fatal with status 127 (evalarith); `(( ))`, `let` and subscripts
  are unchanged.
- A substring of an unset parameter (not `$@`) expands to nothing
  without expanding its offset or length, as bash.
- An expansion error in a redirection, even a fatal one (`${x?}`,
  `set -u`, POSIX-mode arithmetic or readonly), only fails the
  redirection: doredirs catches the escape and the command's status
  is 127 for what would have been fatal, else 1 (Shell.redirfail).
- The lexer follows `shopt extquote` (it was always on). In a
  here-document, `$'...'` is translated only in pattern words, and
  not in a pattern nested inside a `-`/`+`/`=`/`?` word (XC_LITANSI);
  a `$'name'` in a nested `${...}` of a pattern word is the bare name
  with extquote, and the rest single-quoted, error messages included
  (translateansi).
- POSIX mode's `.` never reads a slash-less name from the working
  directory, even with sourcepath off (bash's source_searches_cwd).
- posixexp passes the oracle; posix2, posixexp2 pass, posixexp4 and
  posixexp7 fail only as bash does there.

### Step 7a: fg, bg and %N for running jobs

- Shell.jobctl is bash's job_control: `set -m` turns it on and off
  (histoption), a `( )` subshell, pipeline stage or job starts with it
  off, and a command substitution keeps it (Shell.incomsub notes it).
  Each Job records whether it started under job control (Job.jc).
  `&`'s implicit /dev/null input and lastpipe now follow jobctl rather
  than the -m flag, as bash.
- fg and bg: "no job control" without it (before options); no
  options but `--`; "%N: no such job" or "current: no such job"; "job
  N started without job control"; in a comsub "no current jobs". fg
  of a finished job says "job has terminated"; otherwise it prints the
  command (and "\t(wd: dir)" when it started elsewhere), waits for it
  as a foreground command (traps wait), reports a death by a signal as
  a foreground command's, and drops the job and its status. bg of a
  running job says "job N already in background" with status 0 and
  sets $!; it takes several specs.
- A command whose expanded name starts with `%` is the fg builtin with
  every word as its arguments (bg for a literal `%...` word run with
  `&`, which runs in this shell with no job), ignoring functions and
  redirections as bash does. Not in a simple pipeline stage or a
  background simple command, which bash forks before expanding
  (Shell.forked): there `%1` is "command not found".
- Spec t/exec/904-fg-bg.sh. Stopped jobs come with 7c; until then the
  oracle's jobs test waits forever on fg of a SIGSTOPped job.

### Step 7b: the platform API and the vos model

- api.cpp: Spawn.pgid (0 the shell's group, -1 a new group led by the
  child, else that group), Spawn.fg and Spawn.tty (the child's group
  takes the terminal, set in parent and child); os_setpgid; os_tcpgrp
  (query or set the foreground group); os_kill with a negative pid for
  a group; IO_PROCSTOP, which also reports a stop (WSTOP|sig) or a
  continue (WCONT) without releasing the process; OsInfo.pgid;
  Tty.susp. (WSTOPPED and WCONTINUED would collide with glibc's.)
- POSIX: setpgid and tcsetpgrp in both vfork child and parent with
  signals blocked (joingroup), also for image children; SIGCHLD
  without SA_NOCLDSTOP; IO_PROCSTOP waits with WUNTRACED|WCONTINUED.
- Windows: os_setpgid and os_tcpgrp are E_NOSYS, IO_PROCSTOP is
  IO_PROC (step 8 does job control there in the core).
- vos: VProc.pgid, .stopped (vready skips it, vadvance ignores its
  deadline), .change (the unreported stop or continue) and .stoppend
  (a fatal signal held until continued, as a kernel does). vsignal
  delivers as a kernel: STOP stops anything, a shell included; CONT
  continues and also reaches a shell's traps; TSTP, TTIN and TTOU stop
  a program unless ignored (a shell takes them itself). A process
  stopping itself blocks until continued, or until nothing else can
  run (a deadlock, reported). The terminal has a foreground group
  (VTty.fgpgrp, the outermost shell's by default): ^C and now ^Z go to
  it alone, and a program outside it reading the terminal stops with
  SIGTTIN. Unit test test_jobctl.

### Step 7c: groups, the terminal and stopped jobs

- `set -m` (or an interactive shell with a terminal, which now turns
  monitor mode on as bash) calls jobctlon: from then on, at the
  outermost level of a platform with groups (OsInfo.pgid nonzero), a
  foreground program leads a process group of its own and `&` jobs do
  too (Shell.spawngrp, also for image children). The terminal is fd 2,
  else fd 0, and goes to foreground jobs only when the shell's group
  holds it. An interactive shell leads its own group, takes the
  terminal and ignores TSTP, TTIN and TTOU; a script stays in its
  group, as bash. jobctloff restores the group and terminal at exit and
  ends an interactive shell's stopped jobs (TERM, then CONT). Grouped
  jobs no longer ignore INT and QUIT (the terminal does not reach
  them).
- runprogram waits for a grouped program with taskwaitstop (IO_PROCSTOP
  past continues) and takes the terminal back. A stop makes it a
  stopped job (fgstopped: its text the simple command's), current,
  with status 128+sig. A script prints nothing; an interactive shell
  prints "\n[N]+  Stopped ...". A stop by TSTP breaks every enclosing
  loop; STOP, TTIN and TTOU do not; a function goes on. When the
  terminal's INT killed the program, a loop (or an interactive shell
  without an INT trap) acts as if the shell had it too.
- Waiters of grouped jobs use IO_PROCSTOP: waiterchange notes a stop or
  continue in Task.change and waits again, waking the task waiting
  for the job (wakejoiners, shared with taskentry). polljobs applies
  the change (jobchange): a job that stops becomes current. Job gains
  pgid, stopped and stopsig.
- Current and previous: stopped jobs come first (laststopped), then
  the rules as before. jobs shows "Stopped" with no " &", and jobs -l
  the signal's text ("Stopped (signal)", "Stopped (tty input)", ...);
  jobs -s and -r filter.
- fg gives the group the terminal, continues it, and waits until it
  ends or stops again (joinorstop). bg of a stopped job continues it,
  prints "[N]+ text &" and sets $! to the group. kill %N signals the
  group, adding CONT after TERM or HUP to a stopped job. A stop signal
  the shell sends itself (kill -STOP $$) goes to the kernel, so it
  really stops (or a trap or ignored mode takes it). wait %N on a
  stopped job warns "wait_for_job: job N is stopped" and returns
  128+sig (wait PID silently); plain wait warns "job N[PID] stopped"
  and passes over it; wait -n ignores stopped jobs. disown warns of a
  stopped job. suspend refuses without job control or in a login
  shell without -f, else stops the shell's group with STOP. An
  interactive exit (or EOF) with stopped jobs says "There are stopped
  jobs." once (or running ones under checkjobs); the next exit goes.
- vos: shells in their default mode for TSTP, TTIN and TTOU stop on
  them (VProc.nodfl, from os_sigmode); SIGKILL ends a stopped shell.
  Fixed a pre-existing bug: a signal sent to a shell process before it
  ran left VProc.intr set after the shell took the signal, so its
  next wait failed with nothing pending (a deadlock). Taking signals
  now clears intr.
- Spec t/exec/905-stopped-jobs.sh (one `bash -c` per case; each kills
  what it leaves stopped, since a stopped job holding the recorder's
  pipe would hang it). bash flips between "[1]+" and "[1] " for a job
  killed by TERM after a stop, so that case hides the mark.

### Step 7d: foreground pipelines

- Under job control a foreground pipeline's programs share one process
  group, led by the first started, which holds the terminal: direct
  stages and a simple external last stage join it through
  Shell.spawngrp and spawnfg, so the terminal's ^C and ^Z reach the
  whole pipeline and not the shell.
- The last program is waited with stops (Shell.pipetail). If it
  stops, runprogram reports it across the stage's subshell in
  Sched.stopproc, and pipestopped makes the pipeline a stopped job
  (its text the whole pipeline, its waiter the last program's, its
  group the pipeline's); the other stages run on as orphans. As bash,
  $? is then 128 and PIPESTATUS a lone 0; fg takes the last program's
  status; a TSTP stop breaks loops.
- Not done, by design (the step 7 design forked the whole pipeline or
  `( )` into a child shell): a stage that is shell code, a `( )`, or a
  function cannot stop, so a stop of a program whose last stage is
  shell code waits as bash does when only part of a job stops (bash
  hangs there too in a script; at a terminal ^Z would stop bash's
  forked stage as well). jobs -l lists a stopped pipeline as one line,
  where bash lists each process. Both are in issues.md.
- Spec t/exec/906-stopped-pipelines.sh, also checked on Linux.


### Step 7e: notifications, the jobs and errors tests

- Interactive notification: before each primary prompt, notifyprompt
  lists (as jobs does, on stderr) each of this level's jobs that ended
  or stopped since last shown, then drops the ended ones. The
  non-interactive notifyjobs before each command (killed jobs only)
  leaves interactive shells alone.
- fg applies runprogram's INT rule: a job that dies of the terminal's
  INT counts as the shell's own INT in a loop, or interactively when
  INT is untrapped, so the prompt starts a new line after "^C".
- vos: typing ahead (vtype) moved its key position after delivering a
  byte, so a typed ^Z that stopped the typing process itself left the
  position stale when it resumed, and the ^Z was typed again. The
  position now moves first and the conditions are checked after each
  byte.
- wait -f under job control waits through stops (joinorstop's force);
  a job already stopped still gets wait's warning. Without job control
  -f is plain wait, which never sees stops. A job that ended before its
  continue was seen is not taken as stopped.
- t/edit/057-jobctl.ed, recorded from bash on a pty: ^Z, jobs, fg and
  ^C, bg and the later Done notification, exit's stopped-jobs warning.
  It also passes with our Linux build on a real pty (tools/edrecord
  with EDRECORD_SHELL and EDRECORD_CHECK), the manual terminal check.
- The errors test needed a batch of fidelity fixes, all probed in the
  container and locked in t/exec/907-posix-fatal.sh and
  908-builtin-errors.sh:
  - POSIX mode (non-interactive): a special builtin's error ends the
    shell with its status when the builtin flags it (Shell.bifatal:
    usage errors, invalid identifiers, numeric argument required,
    return outside a function, unsetting a readonly or call-stack
    variable, a readonly assignment through export or readonly, an
    eval or source syntax error), except under command or where set -e
    is ignored (noerrexit). A special builtin's redirection error is
    fatal even there. A readonly assignment before a special builtin,
    alone, or to a for or select variable is ESC_FATAL (127 under -c);
    before another command it abandons the command (ESC_DISCARD). An
    invalid for or select name exits 2. Expansion errors are
    ESC_FATAL. export and readonly stop at their first invalid name.
  - "too many arguments" (exit, return, shift, break, continue,
    history) abandons the text with status 2; -c, a comsub, or a
    subshell under -c then has status 1, as bash's parse_and_execute.
    return counts its arguments before checking it is in a function.
  - alias, unalias, readonly and builtin scan options as bash's
    builtins (scanopts), reporting "-c: invalid option" and the usage;
    alias -p ignores names; readonly takes -a -A -f -n -p, -n meaning
    no readonly attribute.
  - declare -f: -i, -n, -a or -A with names is "-X: invalid option"
    (status 1), and lists nothing without names; name=value that is
    not a function is "cannot use `-f' to make functions"; +r on a
    readonly function is "NAME: readonly function"; attribute changes
    are silent, -F included; a named function prints its body alone
    (the attribute line only with -p or in a listing).
  - hash: "hashing disabled" (status 1) for every form under set +h;
    -d and -t with no name are "option requires an argument", status 1.
  - cd with a readonly PWD or OLDPWD reports it and fails, though the
    directory changes. BASH_ARGC, BASH_ARGV, BASH_LINENO and
    BASH_SOURCE "cannot unset".
  - select checks its name before it sets bash's line, so the error
    cites the line bash last set: the top-level command (where the
    parser stopped), a function call (its body's line), for, case or
    an outer select (Shell.ctlline). A readonly function's
    redefinition cites where the parser got to.
- Oracle: jobs and errors PASS, 69 of 86 (t/oracle-posix.txt).


### Step 8a: interactive jobs, on Windows and everywhere

A survey of job control in an interactive shell on a Windows console
(t/win32 conrun scripts) turned up gaps that were mostly in the core:
- An interactive shell (not a subshell) now names each job it starts
  in the background, "[N] PID" on stderr (announcejob), coprocs too.
- Notification follows bash's notify_and_cleanup points: before each
  prompt; when wait collects a job (collected: reported at once, as
  jobs lists it, then dropped; in POSIX mode at the prompt); and with
  job control between the commands of a `;` or newline list
  (listnotify, not in POSIX mode). Without job control an interactive
  shell drops ended jobs unreported, so job numbers are reused at
  once. A bare wait forgets every status in an interactive shell, $!'s
  too. A script's bare wait reports the killed jobs that ended before
  it (reportkilled), as bash does when it reaps them.
- $- has i after h (bash's flag table order).
- "cannot set terminal process group (N)" shows the group the shell
  went back to (OsInfo.pgid when not its own leader), else -1.
- The terminal's ^C did not interrupt an interactive wait (vos and
  Windows, where it arrives as a group signal): sigsend skipped the
  level's task when it was the scheduler's current task, which a
  blocked task still is while the scheduler takes signals; and the vos
  left a shell's intr clear when the ^C was typed while that shell was
  the current process. taskjoin, which no signal interrupts, now
  clears intr when it ends, so that a ^C during fg does not fail the
  next wait.
- Windows: no blank line after ^C on a cooked console, which echoes
  nothing (Tty.noctl); t/win32/008 also expects interactive exit's
  "exit".
- Windows: fg forwards the console's Ctrl-C and Ctrl-Break to the job
  (fgforward, through os_kill: a shell of this image takes the signal,
  another program ends as by Ctrl-C), since the job was started
  ignoring them and there are no groups; a job ended by INT then counts
  as at a terminal (loop or interactive INT rule).
- Specs: t/exec/909-interactive-jobs.sh (bash -i on a pipe, with and
  without set -m), 910-wait-killed.sh, t/edit/058-wait-intr.ed (also
  passes on a real pty with the Linux build); Windows:
  t/win32/018-jobs.sh (job builtins on real processes, output
  identical to bash's on Linux) and 019-interactive-jobs.sh (conrun).

### Step 9: fidelity sweep

- read -t: the deadline is also checked before each refill, so input
  that never runs dry and never ends a line (/dev/zero, yes with -d '')
  times out with 142 as bash's alarm does. Spec t/posix/002 (the vos
  has no /dev/zero, and its clock does not move while data flows).
- export and readonly: -a and -A make an array only for a word with a
  value, and never convert an existing variable (`readonly -A x` is
  `declare -r x`). A conversion error found while a literal
  name=(...) expands abandons the command at top level (status 1,
  once, under the stale command name), and in a function is reported
  again under the builtin and passed over. Spec t/exec/912.
- POSIX: the terminal's INT, QUIT and TSTP (si_code SI_KERNEL) are
  group signals (os_siggroup), as on the vos and Windows, so they
  reach a running subshell level, not only the outermost.
- Under job control the shell is not in its foreground job's group: a
  subshell level that died of the terminal's INT is treated as a
  program would be (intrjob): only an INT death counts, in a loop or
  untrapped interactively. An interactive loop is abandoned even with
  INT trapped (the trap does not run), and a trapped INT otherwise
  gets the new line bash prints after the echoed ^C. Sigproc.bydefault
  carries "act by default" to runsigs. Spec t/edit/059 (bash, the vos
  and a real pty agree).
- Globbing takes signals before each directory it lists (sigfatal):
  an untrapped Ctrl-C ends a long `**` walk at once. Checked by hand
  on Windows 11 (C:/Windows/**, 13 s, ended 1.5 s in with 130); no
  test, as the walk's length depends on the machine.
- ^C at the prompt with INT trapped: the editor empties the line,
  echoes ^C and returns to the start of the row; fillline runs the
  trap there ($? 130, and 130 after it) and starts a new line, as
  bash. Spec t/edit/060.
- UTF-8 classes and case: unicode.cpp holds tables made from glibc's
  C.UTF-8 by tools/unigen.c (class ranges, upper and lower case runs;
  an exhaustive comparison found no difference). Patterns classify
  and fold multibyte characters (PM_WIDE), case conversion (`${x^^}`,
  `@U`, declare -u/-l/-c) works a character at a time with invalid
  bytes kept, and in regexes bracket classes, `\w \W \s \S` and the
  word anchors take multibyte characters as glibc does (an invalid
  byte is a word character when its Latin-1 value is alnum, \xff as
  ÿ). REG_ICASE raises subject and pattern a character at a time, so
  ı and ſ match I and S. regex_diff no longer skips UTF-8 cases: 0
  differences in 1.2 million random cases (seeds 1, 7, 11, 23). Specs
  t/exec/913 and 914.
- `${!a[@]:N}` and `${!a[*]:N}` on a missing array are an invalid
  indirection, as `${!a:N}` already was; a declared empty array names
  nothing. read -t wraps its whole seconds at 2^32 as bash's timer
  does (2^32+1 is one second, 2^32 sets no timer), and rejects only
  what overflows 64 bits. Spec t/exec/915.
- return checks its argument first, as bash's get_exitstat: a
  non-number is reported before "too many arguments" and before "can
  only `return'" (both printed at top level, status 2, going on); a
  number with more after it abandons the command, as before. The
  mapfile callback case (m4.md) already agreed. Spec t/exec/916.
- let and an associative key whose shell quoting is left open (`let
  "++a[$b]"` with b="80's", m4.md): reported twice as a bad array
  subscript and read as unset, the assignment "not a valid
  identifier", the expression going on (status 0 for ++), as bash;
  we had taken the key as 80s. Spec t/exec/917.
- Namerefs (m4.md): a scalar assignment through a nameref sets the
  binding seen from the nameref's scope even when a newer function
  shadows it (Bind.depth, SV_ATDEPTH); elements and compound
  assignments still use the visible binding, as bash's array paths
  do. declare's readonly message names the nameref for an assignment,
  the target for attributes alone or a failed local. A failed
  assignment to a valueless readonly nameref at top level marks it
  V_EMPTYREF, after which +r does nothing silently. The suite's
  nameref test now passes (t/oracle-posix.txt). Specs t/exec/918, 919.
- `~user` is the user's home from /etc/passwd (read through the file
  layer, so the vos has the oracle image's accounts, and the homes of
  them that exist there), in words, after : in assignments and in
  BASH_ENV; `~` with HOME unset is the shell's own user's home, no
  longer a made-up /home/oracle. Completion of a ~word without a
  slash, M-~ and C-x ~ list the users as readline does, homes marked
  and appended to as files. Specs t/exec/920, t/edit/061.
