# M9: w64devkit

Status: done (step 7 has the closing checks).

Scope and exit criteria: the M9 row of plan.md's milestone table:
Dockerfile build, bash/sh/ash/lash names, `w64devkit.c` launches the
new shell, original man page, x64 and x86 releases. Exit: w64devkit
runs entirely on unabashed; busybox `ash` removed from the alias list.

## Where things stood at the start (bf02049)

- unabashed builds with one g++ command per target (Makefile), x64 and
  i686, kernel32 imports only, PE subsystem 5.02/5.01. The persona
  comes from argv[0]: sh, ash and lash (any case, .exe or not) are
  native mode, anything else msys mode (bash), and an etc/fstab beside
  the install root forces msys mode.
- tools/w64trial (M5a) already mirrors a w64devkit with our shell as
  sh.exe and builds autoconf projects with it: make 4.4.1 and xz 5.6.4
  configure, build and pass `make check`, with equal configurations.
- w64devkit (~/src/w64devkit, master at 667d0d3) builds in Docker
  (Debian trixie, GCC 16.2 cross compilers built in the image). Its
  shell is busybox-w32: bin/sh.exe, ash.exe, lash.exe and the other
  applets are copies of busybox-alias.c, a stub that starts busybox.exe
  with the same command line; w64devkit.exe (src/w64devkit.c) starts
  `busybox.exe` with the command line `sh -l`. The kit's pages are
  hand-written man(7) under man/, formatted by the kit's nroff and
  shown by busybox man; man/README.md is the style guide.
- No w64devkit build cache in WSL's docker: a release build downloads
  every source (GCC, binutils, mingw-w64, gdb, ...) and builds the
  cross toolchain, hours of work.


## Principles

1. w64devkit is the user's project: changes go on a branch there
   (`unabashed`), committed but not pushed or merged, each step tested
   on a local kit before it is committed.
2. Nothing in w64devkit's tree depends on unabashed being published:
   the Dockerfile takes the source as a tarball like every other
   dependency, and where that tarball comes from (a release URL and
   its sha256) is the user's decision, left as a marked placeholder.
3. The man page is our own words, written from our code and behaviour,
   never from bash's manual (GPL), in the kit's man(7) style.
4. The busybox applets stay; only the shell names move. busybox's own
   `sh` applet remains reachable as `busybox sh`.


## Steps

1. **Release build and names.** A `make dist` source tarball (git
   archive, no tests' bash files), and the release build lines the
   Dockerfile uses (the same flags as the Makefile's). How the four
   names are installed: each a copy of the one image (the persona
   needs argv[0], and make starts `sh -c` per recipe line, so a stub's
   extra process would cost every line; 7z's solid archive stores the
   copies once).
2. **Launcher.** w64devkit.c starts bin/sh.exe with `sh -l`, and
   busybox only if sh.exe is missing; the alias list loses sh, ash and
   lash; etc/profile (busybox-specific comments, libtool workaround)
   checked under our shell.
3. **Man page.** man/man1/unabashed.1 in the kit's style: invocation
   and the personas, the Windows path rules of each mode, options,
   startup files, environment, what differs from bash, exit status;
   stubs bash.1, sh.1, ash.1 and lash.1. Lint clean with the kit's
   nroff -w (and groff/mandoc if their images are at hand).
4. **Kit trial.** A local kit mirrored from the installed w64devkit
   with the branch's launcher, our four names and the new page: an
   interactive session from w64devkit.exe driven by winctl (profile,
   prompt, editing, man, Ctrl-C, exit), make and configure of local
   projects, busybox sh absent from the process tree; the i686 build
   on the XP laptop the same way.
5. **MSYS2 programs and bridges.** The M9 issues: study what Cygwin
   programs accept for a procsub's path and for descriptors above 2;
   fix what is reachable, accept the rest with reasons.
6. **Dockerfile.** A build-unabashed stage on the branch, for both
   variants, from the tarball of step 1; checked by running the same
   commands with the kit's own compilers. A full release build waits
   for the user (downloads and hours of toolchain building).
7. **Closing.** Exit criteria checks, issues.md has no M9 items.

## Implementation

### Step 1: release build and names

- `make dist` writes `unabashed-YYYYMMDD-HASH.tar.gz` (git archive of
  HEAD, prefix `unabashed-YYYYMMDD-HASH/`, 2.2 MB, ignored by git).
  Built from the extracted tarball with the cross compilers' names, as
  the Dockerfile will (`x86_64-w64-mingw32-g++` and
  `i686-w64-mingw32-g++`, the Makefile's FLAGS and WIN32, plus the
  i686 subsystem and large-address flags): kernel32 imports only, 1.41
  MB and 1.24 MB, 23 s for the x64 build on this machine.
- README's build line lacked the 16 MiB stack (`--stack,0x1000000`)
  that main_win32.cpp's header and the Makefile give.
- The names are four copies of one image (sh, ash, lash: native mode;
  bash: msys mode), decided in Steps above.

### Step 2: launcher

- w64devkit (branch `unabashed`): w64devkit.exe starts `bin\sh.exe`
  with the command line `sh -l` instead of `busybox.exe`; in an older
  kit sh.exe is busybox's alias stub, which takes the same command
  line, so the launcher works with either. The Dockerfile's alias list
  no longer makes sh, ash and lash.
- w64devkit's busybox patches that concern the shell are already our
  native mode's behaviour: the login shell reads
  `<sysdrive>/etc/profile` and `<exe>/../etc/profile` and does not
  change to HOME (system-profile, login-no-chdir); noiconify is
  busybox's own console option.
- A trial kit, scratchpad mkkit.sh (Windows 11: junctions and hard
  links, as w64trial) and mkkitxp.sh (XP: `cp -al`, which has no
  mklink; a hard link of a running image cannot be unlinked, so the
  replaced files are renamed out of the kit): w64devkit.exe starts our
  sh.exe, ps shows no busybox shell, Ctrl-C at `sleep 5` gives 130.
- Found on XP: native mode set TERM=dumb when unset, as bash does,
  which made the editor draw sideways (horizontal scrolling) on a
  console. busybox-w32 leaves TERM unset; native mode now does too
  (msys mode keeps Git Bash's xterm-256color).
- Found on XP: the shell's own output to a console without VT (XP, 7,
  or conhost without VT processing) printed escapes raw, so a profile's
  title (`printf '\e]2;...\a'`) and colours showed as `←]2;...`, and
  the editor's column count went wrong after them. busybox-w32
  emulates them for its own output. fdwrite now sends output for such
  a console (a File's cached tty state 3, from os_tty's legacy) through
  a Shell-wide VtCon, and vtcon sets the window title for OSC 0 and 2
  (CON_TITLE, SetConsoleTitleW). The vos's console without VT now
  shows a raw ESC as `←`, as conhost does, so t/edit's vtcon runs catch
  raw escapes; t/edit/081, recorded.

### Step 3: the kit's bash, and the manual page

- w64devkit's bash.exe (msys mode, no etc/fstab, no usr/bin) had no
  /tmp: without an fstab /tmp is `<root>/tmp`, as in a bare MSYS2, and
  the kit has none, so an agent's `/tmp/...` (Claude Code keeps its
  cwd file there) failed. With no fstab /tmp is now the user's
  temporary directory (TEMP, else TMP; case-insensitive and fixed, as
  Git for Windows' usertemp line), beside the existing no-fstab rules
  (drives at /c, /bin the shell's own directory). A test personality
  `w64bash` (C:/w64/bin/bash.exe) and t/winvos/030, hand-checked.
- Open decision, recorded rather than changed: native mode (sh, ash,
  lash) never enters bash's POSIX mode, though m5a.md's decisions say
  argv[0] `sh` selects it; startup's busybox branch returns before
  that. It matches busybox ash, and every configure and make trial
  ran this way.
- The manual page is w64devkit's own man/man1/sh.1, rewritten, rather
  than a new unabashed.1: the kit already has ash.1 and lash.1 as
  `.so man1/sh.1` stubs and its pages are named by command, so sh.1
  carries the text and bash.1 is a new stub (w64devkit a78de64).
  Sections: names and modes, invocation, startup files, paths in each
  mode, running programs, line editing, jobs and signals, differences
  from bash; options, environment, exit status, examples. It points to
  GNU's Bash Reference Manual and `help` for the language rather than
  restating it. busybox.1 no longer calls the kit's sh busybox's ash:
  busybox's shell is `busybox sh`, and of the BB_* variables our sh
  reads only BB_OVERRIDE_APPLETS. Both pass the kit's `nroff -w`;
  `man bash`, `man ash` and `man sh` show it in the trial kit (with
  the trial kit first in PATH: busybox finds pages beside its own exe).
- Superseded (2026-11-08): the page moved to unabashed.1 at the root of
  this repository, so it ships in the `make dist` tarball and the kit's
  Dockerfile installs it as u-config.1 is installed; the kit's sh.1,
  bash.1, ash.1 and lash.1 are all `.so man1/unabashed.1` stubs. It was
  rewritten from a source fact inventory, much deeper on msys against
  native mode, and every section verified against the code and by
  running both personas (two rounds), which fixed several small bugs
  first and logged the rest in issues.md. Its .TH carries the kit's
  "w64devkit Manual" footer since that is where it is read.

### Step 5: MSYS2 programs and bridges

- busybox diff read a bridged procsub as empty (t/win32/015 recorded
  it so). The cause: busybox-w32's stat opens a file and reads its
  first KiB to decide its execute bit, and diff stats both paths
  before opening them, so the stat took the data. It skips that read
  for a name ending in `.dll`, so the bridges' pipes are now named
  `\.\pipe\unabashed-PID-HEX.dll`. Any busybox applet that stats
  before reading was affected (`sh -c 'stat "$1"; cat "$1"'` printed
  nothing); 015 now records diff's real output.
- MSYS2 and Cygwin programs get a temporary file for a `/dev/fd/N`
  argument (exec.cpp, starttemp/endtemp), since the named pipes failed
  them in every way step 8 of M5a tried. A new platform call,
  `os_namedtemp(dir)`, makes a file under a fresh name in the user's
  temporary directory, delete-on-close and shared, so the program
  opens it by name while the shell holds it and it goes with the
  shell's handle (also if the shell dies). Reading: the shell reads
  the descriptor to its end into the file first (up to 1 GiB, then it
  gives up and leaves `/dev/fd/N`); writing: after the program exits,
  the file's contents go to the descriptor. The vos models it (a node
  detached from its directory when the handle closes).
  Checked with Git's cat, diff, tee, head and wc (`tee >(tr a-z A-Z)`,
  `diff <(…) <(…)`, an empty procsub, 3 MB, and nothing left in
  TEMP afterwards); t/winvos/031, hand-checked.
- A direct pipeline stage (one started with no vproc) with a
  `/dev/fd/N` argument for an open descriptor now retries as a stage
  of shell code, which bridges it, as an E_NOEXEC script does
  (`exec 3<f; busybox head /dev/fd/3 | cat` passed /dev/fd/3 before).
  Procsubs never ran direct (runscode), so this only concerned
  descriptors opened earlier.
- Accepted, with reasons, in issues.md: a procsub is a file for MSYS2
  programs (no overlap, the file's name shows, 1 GiB), descriptors
  above 2 never reach them, and the remaining bridge limits. issues.md
  has no M9 items.
- t/win32/run's WORKDIR must be outside %TEMP%: the shell as bash now
  has /tmp there (step 3), and by Cygwin's mount order (longest POSIX
  minus native first) a path under TEMP is /tmp/... even when it is
  also under the install root, as Git Bash shows it. 015 failed for
  that reason with the scratchpad's workdir; ~/src/scratch/ub-w32 is
  used now.
